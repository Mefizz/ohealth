## 1. Executive summary

**Estimated coverage: 72%.**

Scoring method: 36 independently observable TV controls were assessed; ✅ = 1, ⚠️ = 0.5, ❌/❓ = 0. The score is an implementation estimate, not an official certification result. API behavior that can only be confirmed against eHealth remains marked partial or unclear.

The module has broad functional coverage: create/sign APIs, local persistence, three activity kinds, activity payload formatting, requisition search, plan/activity details, outcomes, lifecycle transitions, approval creation/listing/revocation, Ukrainian warnings, and substantial tests. The strongest implementation areas are eHealth endpoint coverage, approval payload construction, activity detail rendering, and cancel/complete prechecks.

The principal compliance risk is that important TV constraints are not consistently enforced server-side. Care plan creation does not require an encounter in validation, derives the author from the currently authenticated user's writer employee instead of the encounter author, and can send directly to eHealth before a local draft exists. Activity draft creation does not explicitly verify a granted write approval, and some required product/quantity/program conditions remain UI- or eHealth-dependent. Role handling is also inconsistent for `MED_COORDINATOR`.

Legend: ✅ done · ⚠️ partial · ❌ missing · ❓ unclear

## 3. Priority implementation gaps

### P0 — certification / integrity blockers

1. **Make encounter mandatory and derive immutable server fields from it.** Require a valid finished eHealth encounter; derive `author` from encounter author `employee_id`; derive only the TV-defined primary diagnosis into `addresses`; reject patient/encounter mismatch.
2. **Enforce the local-draft-before-eHealth invariant.** On every create flow, persist the draft and stable UUID before signing/submission. Remove or consolidate the divergent `CarePlanManager::signPlan()` path so all draft signing uses one compliant payload builder.
3. **Add server-side activity authorization gates.** Before create/edit/delete/sign, authorize `manage`, verify a granted `write` approval for the exact employee, and explicitly compare plan author/activity author/current employee legal entities.
4. **Harden required activity fields.** Validate kind with `in:medication_request,device_request,service_request`; require appropriate product form; require medication program and verify active `type=MEDICATION`; enforce quantity/unit requirements by kind. Correct classification-only device validation so `product_codeable_concept` can replace `product_reference`.

### P1 — likely TV findings

1. Show the exact `period.end` warning when the field is populated and before any KEP submission, not only during later approval-method selection.
2. Support `MED_COORDINATOR` consistently in the explicit role gate and author-selection logic, or document/evidence why this role may initiate but not author the plan.
3. Make no-program `scheduled_period` omission safe; avoid date conversion on blank values and test both program/no-program branches.
4. Force or strongly prompt eHealth synchronization before cancel/complete prechecks so stale local request/activity states cannot permit an invalid transition.
5. Add focused tests for requisition search and eHealth-by-id retrieval/sync.

### P2 — maintainability and evidence

1. Replace hard-coded medication/device program UUID defaults with validated dictionary-driven selection.
2. Consolidate duplicate create/sign payload construction and status normalization.
3. Add route-level scoped binding for activity under care plan.
4. Add a TV 3.10 role/permission matrix test and end-to-end mocked workflow tests for draft → KEP create → approval → activity → outcome → plan completion.
