# TV 3.9 Medication e-prescriptions («Облік ЕР на ЛЗ») audit

Audit date: 2026-09-14  
Method: static, read-only code/test review; no tests were run.  
Audited branch: `i768_i789_care_plan_erx_referral` at `b638cff3`.

## Summary

TV 3.9 is substantially implemented for creating and managing a Medication Request Request from a care-plan medication activity. The current branch adds important i768/i789 work: FHIR Identifier-backed `based_on`/`context` references, patient eRx registry mapping, encounter selection restricted to today's finished encounters by the current performer, correct signed-content transport, success copy, and remaining-quantity warnings.

It is not yet TV-complete. The main risks are authorization and path consistency: patient-registry eHealth actions have no medication-request permission checks, care-plan actions authorize only `care_plan:write`, and standalone encounter creation does not enforce the today/current-performer rule server-side. Search exists, but patient-level details/reject/resend and the care-plan-context access matrix are incomplete. Medication pricing/catalog output is absent.

## Access matrix observed

| Role | Configured medication scopes | Effective UI/application behavior |
|---|---|---|
| DOCTOR | read/details/write/sign/reject/resend | Expected scopes exist; care-plan actions do not check them individually. |
| SPECIALIST | read/details/write/sign/reject/resend | Same as Doctor. |
| MED_ADMIN | read/details/reject/resend; no write/sign | Can reach patient registry. Care-plan mutation depends on `care_plan:write` (not configured), but patient eHealth search has no medication-specific check. |
| ASSISTANT | read/details/resend; no MRR write/sign/reject | Has `care_plan:write`, so current care-plan component authorization can allow create/sign/reject despite missing medication mutation scopes. |
| RECEPTIONIST | no medication request scopes | Has `person:read`, so the patient medication route/local registry is reachable and eHealth search can be invoked at application level. |
| PHARMACIST | pharmacy-specific details/read/block/unblock/reject plus dispense | Pharmacy index has a dedicated route/action gate. This does not protect patient/care-plan clinician paths. |

## Gaps by priority

### P0

1. **Standalone eligibility bypass:** `createEncounterDraft()` does not verify today's finished encounter and current performer. A direct Livewire call can create from an older or other-performer finished encounter.
2. **Care-plan action scope bypass:** create, sign, reject, resend, and printout rely on `care_plan:write`/plan ownership rather than their medication-specific scopes. In particular, ASSISTANT has care-plan write but lacks MRR write/sign/reject scopes.
3. **Patient registry authorization gap:** the route/component requires only Person view. Users with `person:read` but no medication request scope can read local eRx data and invoke eHealth search/save methods.

### P1

1. Patient-level Medication Request details are absent; `toggleExpand()` is dead code.
2. Patient-level reject/resend/printout actions and care-plan-context retrieval are not wired.
3. Program `request_max_period_day` is warning-only; standalone does not enforce it.
4. Standalone flow lacks `max_request_dosage`, maximum/recommended daily-dose, and `(!)` confirmation logic.
5. Medication price/reimbursement catalog is missing.
6. Action/status/legal-entity/role access matrix and denial tests are missing.

### P2

1. Care-plan drug “Змінити” / “Додати” controls are inert.
2. Packaging selector is capped at ten multiples instead of representing all valid quantities up to the allowed limits.
3. Exact TV action wording “Sign Medication Request Request” is not represented in the UI.
4. The dedicated post-sign remaining-quantity panel is in a closed drawer; the warning currently relies on transient flash/toast display.
5. Status filters omit several modeled states (`pending`, `processing`, `signed`, `blocked`, `expired`).
