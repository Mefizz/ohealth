# TV 3.22 — Device Dispense in Encounter Package

## Summary

**Overall result: NOT COMPLIANT / UI scaffold only.**

The Encounter Package exposes a “Видачі медичних виробів” section, but the section contains hard-coded demonstration data and unbound controls. There is no Device Dispense form state, validation, FHIR mapper, repository/model, eHealth API client, persistence path, or inclusion in the signed Encounter Package. The patient-level Device Dispense registry is also a mock: it initializes one hard-coded record and its `search()` method is empty.

Existing device-request and program-catalog code can provide patterns for a future implementation, but it does not implement TV 3.22. Device-dispense scopes are configured for relevant roles/legal-entity types; scopes alone do not make the workflow functional.

Audit scope was the primary working tree only. No tests were run and no application files were changed.

## Additional evidence

- `app/Livewire/Person/Records/DeviceDispenses.php:27-46` initializes a hard-coded pacemaker dispense; `search()` at `:48-51` contains only a placeholder comment.
- The patient registry’s detail action is `javascript:void(0)` (`resources/views/livewire/person/records/device-dispenses.blade.php:288-296`), so it does not provide a functional read/details path.
- Device-dispense scopes (`device_dispense:write`, `read`, `complete`, `stop`, `mark_in_error`) are present in `config/scopes/roles.php:20`, providing authorization configuration but no application workflow.
- The bundled device program documentation states that `dispense_allowed` controls whether Device Dispense may be created for a DEVICE program (`storage/app/device_docs.md:122-133`). No corresponding check is used by the Encounter Package.

## Gaps and implementation direction

1. **Domain/API layer absent.** Add a dedicated Device Dispense eHealth API client, mapper, local model/repository/schema (if local drafts are required), and remote sync handling.
2. **Encounter Package integration absent.** Add a Livewire form collection and include it consistently in validation, builder, draft persistence, loader/edit flow, signed snake_case payload, and job synchronization.
3. **Dispense quantity rules absent.** Resolve source Device Request quantity and prior dispenses; enforce integer `> 0`, remaining quantity, ЗОЗ partial/full behavior, and pharmacy full-only behavior. Treat TV 3.5.2 as a prerequisite for the program→pharmacy path.
4. **Program-device selection absent.** Query only active devices participating in the source request’s DEVICE program and allowed for dispense; enforce definition/type/model/brand consistency and exactly one payload representation.
5. **UX and test proof absent.** Replace demo markup/data with bound controls and records, field-level eHealth errors, accurate submit success, and tests covering full/partial, forbidden partial pharmacy dispense, invalid quantities, non-program devices, XOR mapping, all required references, success, and API failure.
