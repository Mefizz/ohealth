## 2. Аналіз 404 після підписання

### Сам шлях GET відповідає документації

Публічний контракт eHealth містить:

```text
GET /api/patients/{patient_id}/service_requests/{service_request_id}
POST /api/patients/{patient_id}/service_requests
GET /api/jobs/{id}
```

Джерела: [MEDICAL EVENTS MIS API](https://medicaleventsmisapi.docs.apiary.io/#reference/service-requests), [машиночитаний опис Apiary](https://jsapi.apiary.io/apis/medicaleventsmisapi).
Контракт звірено під час аналізу. Сам по собі наданий 404 не доводить помилку маршруту або конкретну причину невдалого створення.

### Підтверджена помилка: `/Jobs/` не розпізнається

Документований приклад відповіді створення:

```json
{"data":{"status":"pending","links":[{"entity":"job","href":"/Jobs/NBXk9EyErUZv1RhXgyvgg"}]}}
```

`app/Services/MedicalEvents/EHealthJobResolver.php:40` перевіряє тільки `links[0].href` через регістрозалежний `str_contains($jobHref, '/jobs/')`. За відсутності окремого `job_id` посилання `/Jobs/...` не розпізнається, і `resolve()` повертає початковий `pending` без жодного polling.

Далі `ReferralRequestLifecycleService.php:709`–`:728`:

1. Розгортає відповідь, яка може залишатися оболонкою job.
2. Для `pending`, `processing`, `accepted`, `queued` та невідомої порожньої відповіді обирає локальний статус `active`.
3. Зберігає запис і виконує GET для отримання номера направлення.
4. Помилку GET перехоплює як помилку додаткової синхронізації; зовнішній компонент усе одно може показати успіх.

Це реальний шлях до передчасного GET і хибного успіху. Чи саме він спрацював у наданому випадку, потрібно звірити з відповіддю POST та журналом polling цієї операції.

### Додаткові дефекти у тому самому ланцюжку

- Resolver переглядає тільки перше посилання: `job` на іншій позиції також пропускається.
- `extractSignedCreateEntity()` повертає всю оболонку, якщо не знаходить вкладену сутність. `persistAfterSignedCreate():724` без перевірки призначення поля бере її `id` як UUID направлення. Якщо це ID job, UUID буде підмінено.
- При зміні UUID `store()` робить upsert за новим UUID, тому старий рядок чернетки може залишитися. Існуючий тест `ReferralLifecycleTest::test_sign_referral_does_not_require_status_reason` навіть моделює різні UUID чернетки й відповіді, але не перевіряє відсутність другого рядка.
- `ManagesEncounterReferrals.php:302` повторює GET номера після аналогічної спроби всередині lifecycle-сервісу, тому один збій може дати два однакові запити.
- `trySyncDraftFromEHealth():419` трактує будь-яку `EHealthResponseException` або validation error як «не синхронізовано». Проблеми доступу та помилки сервера не повинні автоматично відкривати шлях до повторного створення.
- GET для локальної, ще жодного разу не відправленої чернетки закономірно може повертати 404. Його потрібно відрізняти від 404 після підтвердженого створення.

## 3. План реалізації

### Крок 1 — відновити коректне завершення підписання

1. У `EHealthJobResolver` шукати посилання job у всьому масиві `links`, враховувати `entity`, різний регістр `/Jobs/`, `/jobs/`, `/api/jobs/`, абсолютний URL та окремий `job_id`.
2. Розбирати шлях URL; зберігати opaque ID job як рядок, не вимагати UUID. Запити виконувати через налаштований eHealth-клієнт; не переходити на довільний зовнішній host із відповіді.
3. Відрізняти синхронну клінічну сутність від асинхронної оболонки. `pending` без придатного job-посилання має давати явний стан незавершеної операції, а не успіх.
4. У `persistAfterSignedCreate()` дозволяти завершення лише після підтвердженого успіху. Брати UUID лише з перевіреної сутності або відповідного `links[].entity=service_request`; за відсутності нового UUID зберігати той, що вже підписали.
5. Після успішної job без клінічного payload отримувати направлення за його UUID; не підміняти його ID job. Якщо номер ще не доступний, показувати стан завершення синхронізації й повторювати лише читання.
6. Залишити одну точку отримання номера у lifecycle-сервісі, прибрати дублювання з компонента взаємодії.

### Крок 2 — зробити повторні спроби керованими

1. Для заявки зберігати стан відправлення та дані job: `ehealth_job_id` (nullable string), `ehealth_job_href` (nullable string), `submission_state` (draft/submitting/pending/succeeded/failed). Для спільного service/device шляху узгодити обидві моделі й міграції.
2. При timeout/перезавантаженні відновлювати polling існуючої job; при підтвердженому успіху синхронізувати ресурс. Звичайне повторне відкриття не повинно знову робити POST.
3. Атомарно перевіряти й переводити заявку у `submitting`, щоб паралельні кліки не запускали два підписання. Не тримати транзакцію БД протягом мережевого polling.
4. Для невизначеного результату POST, коли відповідь із job втрачено, використовувати той самий UUID і процедуру перевірки/узгодження з eHealth. Не генерувати нову заявку, щоб обійти помилку.
5. Перед підписанням перевіряти стан на сервері в усіх трьох точках: взаємодія, план лікування, реєстр направлень пацієнта. Відправлений документ не редагувати як локальну чернетку.

### Крок 3 — перенести патерн редагування працівників

1. Запровадити спільний `saveDraft` для направлень зі стабільним локальним ID/UUID. «Зберегти» та «Зберегти й підписати» мають відрізнятися тільки наступним відкриттям КЕП.
2. При відкритті наявної чернетки повністю відновлювати форму: послуга, категорія, кількість, програма, дати, пріоритет, примітки, інструкції, обґрунтування, спосіб інформування.
3. Після першого create записувати ID/UUID у стан компонента й передавати його в наступні збереження. При явному створенні нового документа очищувати цей стан.
4. Пошук для відновлення обмежувати пацієнтом, закладом/доступним автором, взаємодією або activity та типом документа. Кілька чернеток різних послуг не зливати через спільного пацієнта чи encounter; за неоднозначності відкривати вибрану заявку.
5. Перед підписанням зберігати актуальні зміни у ту саму чернетку. Для плану лікування замінити поточний перехід прямо до КЕП на відновлення редагованої форми.
6. Оновлювати існуючий локальний рядок за первинним ключем, навіть якщо перевірена відповідь eHealth вимагає узгодити remote UUID; окремо обробляти конфлікт з уже синхронізованим рядком.
7. Перевірку залишку та запис чернетки виконувати в одній короткій транзакції з блокуванням activity. При редагуванні виключати поточну заявку з уже зайнятої кількості; поточний guard завершує транзакцію до запису чернетки.

### Крок 4 — прибрати дублювання призначень послуг

1. У `persistActivityDraft()` після create встановлювати `activityForm['id']` і зберігати його при поверненні з КЕП або помилці підписання.
2. При відкритті редагування завантажувати саме вибране локальне призначення; перевіряти належність поточному плану та можливість редагування його стану.
3. Обидві кнопки збереження мають оновлювати те саме призначення. Окрема дія створення нового призначення починає нову форму.

## 4. Перевірки та критерії приймання

| Сценарій | Очікуваний результат |
| --- | --- |
| Двічі «Зберегти», потім «Зберегти й підписати» | Один локальний рядок, незмінні ID/UUID, останні зміни входять у підпис |
| Закрити КЕП, відкрити чернетку й змінити поля | Відновлена редагована форма, оновлення того самого запису |
| Перезавантаження сторінки, підписання з реєстру пацієнта | Відкривається та сама заявка; уже відправлена операція відновлюється |
| `/Jobs/id`, `/jobs/id`, `/api/jobs/id`, job не в першому links | Polling виконується до термінального результату |
| Job failed, timeout, pending без посилання | Немає хибного `active` та повідомлення про успішне створення |
| Job processed із result/data або тільки resource link | Правильний UUID направлення та номер; ID job не потрапляє у направлення |
| GET номера повертає 404 після підтвердженої job | Повторюється синхронізація читання; новий POST не створюється |
| Відповідь містить інший перевірений remote UUID | Оновлюється той самий локальний запис, без залишеної другої чернетки |
| Подвійний клік / дві вкладки | Одна відправка для тієї самої заявки; залишок activity не перевищено |
| Дві різні послуги або явне нове направлення | Окремі законні заявки не зливаються |
| Призначення: save → save-and-sign → закриття КЕП → save | Один рядок `care_plan_activities` з актуальними полями |
| Чужа заявка або вже відправлений документ | Збереження/повторне створення відхиляється відповідною перевіркою |

Розширити `EHealthJobResolverTest`, `ReferralRequestLifecycleWriteTest`, `ReferralLifecycleTest`, `EncounterStandaloneReferralCreateDiagnosticTest`, `PatientReferralsPhase6Test`, `CarePlanShowActionsTest`. Для перевірки лімітів і паралельності потрібні тести БД; для контракту HTTP — `Http::fake`, а не тільки mock `getData()`.

Після виправлення спільного resolver прогнати наявні перевірки його інших споживачів: device requests, рецепти, approvals, операції завершення/скасування. Завершити ручною перевіркою створення з КЕП у preprod у трьох точках входу.

## 5. Межі поточної перевірки

- Статично простежено шлях від форми до POST, polling, локального збереження та наступного GET.
- Окремою Python-перевіркою на документованій відповіді підтверджено, що поточна регістрозалежна перевірка пропускає `/Jobs/...`; це перевірка умови, а не виконання PHP-застосунку.
- У середовищі немає PHP, Composer та встановленого `vendor`, тому PHPUnit і сам застосунок не запускалися.
- Доступу до журналів конкретного POST/job та БД колеги немає. Потрібні лише очищена відповідь створення й пов'язані записи polling, щоб підтвердити точний шлях наданого інциденту.
