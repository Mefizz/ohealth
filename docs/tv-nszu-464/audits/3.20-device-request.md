# TV 3.20 — Device e-requests compliance audit

Audit date: 2026-09-14  
Scope: static, read-only audit of the primary workspace only. No tests or runtime/API calls were performed.

## Summary

TV 3.20 is **partially implemented but not acceptance-ready**. The strongest path is issuing a DeviceRequest from a care-plan `device_request` activity: the application can search program DeviceDefinitions, enforce packaging/remaining quantity, prequalify, build a signed flat DeviceRequest, submit it to the patient-scoped eHealth API, persist it, show it in the patient registry, resend SMS, and mark it entered in error.

The dedicated `/device-requests` page is only a placeholder/legacy draft flow and is not a viable TV workflow. There is no standalone DeviceRequest flow from a same-day self-authored encounter (including ДЗР without a program), no eHealth-backed DeviceRequest search API, and no executor lifecycle (revoke/complete/dispenses). Critical create fields are also dropped: `inform_with`, request parameters, and the explicit request reason are not included in the signed DeviceRequest. The generic printout is not an A5 DeviceRequest form.

Key implementation evidence:

- Care-plan flow: `app/Livewire/CarePlan/Concerns/ManagesCarePlanReferrals.php`
- Mapper/sign payload: `app/Services/MedicalEvents/Mappers/DeviceRequestMapper.php`
- Patient-scoped API client: `app/Classes/eHealth/Api/Patient/DeviceRequest.php`
- Registry/actions: `app/Livewire/Person/Records/PatientReferrals.php`
- Placeholder page: `app/Livewire/DeviceRequest/DeviceRequestIndex.php`, `resources/views/livewire/device-request/device-request-index.blade.php`
- Stub dispenses: `app/Livewire/Person/Records/DeviceDispenses.php`

Status legend: **PASS** = implemented with relevant safeguards; **PARTIAL** = meaningful implementation but acceptance gaps; **FAIL** = absent, placeholder, or materially non-compliant.

## Gaps by priority

### P0 — blocks the core acceptance flow

1. **Signed DeviceRequest loses `inform_with`, reason, and parameters.** The form captures some of this data, but the device model/repository/mapper cannot persist or sign it.
2. **No standalone same-day/self encounter DeviceRequest flow, including ДЗР without a program.** `createEncounterDraft()` has dormant device support, but no Livewire UI/action reaches it.
3. **Lifecycle coverage is incomplete:** no DeviceRequest revoke or complete implementation and DeviceDispenses is a static stub.
4. **Active-only preconditions are not enforced server-side.** Care-plan/device activity issuance accepts broader states and lacks explicit today/self encounter checks.
5. **The dedicated DeviceRequest page is a placeholder/legacy flow.** It uses hard-coded program/type inputs and a different old API lifecycle, while its list is intentionally empty.

### P1 — likely TV failures or unsafe behavior

1. No enforcement of medical-program `request_max_period_day`.
2. Auth-method retrieval failure/empty list does not block creation with the required OTP guidance.
3. Search/details use only local rows and cannot discover or fully inspect eHealth DeviceRequests.
4. Generic print HTML is not a compliant A5 DeviceRequest printout.
5. Success messages do not vary by authentication method and program presence; some device outcomes are mislabeled as referrals.
6. Contract participation lookup failure is warning-only, permitting issuance without confirmed participation.
7. Mark-in-error uses a generic cancel path with hard-coded reason and sparse DeviceRequest-specific tests.

### P2 — quality and consistency

1. Device rows resolve UUID products/programs to generic “Медичний виріб” / “—” instead of catalog names.
2. Device status rendering often reuses `ServiceRequestStatus` rather than `DeviceRequestStatus`.
3. Terminology alternates among “е-запит”, “електронний рецепт”, and “направлення”.
4. The legacy organization-level `/api/device_requests` client and patient-scoped client create divergent implementations.
5. Existing tests focus on mapper shape and mocked happy paths; no end-to-end TV matrix covers auth × program, max period, failure states, A5 print, lifecycle actions, or real dispense search.
