# TV 3.8 audit — PR #645 (МВН + МВТН)

Audit target: `openhealths/nationHealth#645`, branch `i644_composition_medical_conclusions`, commit `c49025959a12f0f0cb4cc80753b1c7984b92a1af`.

Evidence was read only from `/home/mefizz/projects/ohealth/.worktrees/tv_38_compositions`. The application code was not changed. This report is the only written artifact.

## Executive summary

PR #645 contains a broad implementation of the TV 3.8 surface: both composition types, API client methods, payload mapping, Livewire forms, async create/sign UI, read/print/search, cancellation UI, ERLN integration status/retry, pregnancy-period UI, preperson restrictions/warning, policies, persistence, and 50 changed files with a substantial focused test set.

It is **not sufficient for TV 3.8 acceptance in its current commit**. The primary create flow is internally inconsistent and appears non-functional: the UI references a nonexistent `submitComposition` method, while the actually callable `reviewDetails()` sends the unsigned FHIR array directly to an API method whose contract and tests require `['data' => <base64 PKCS#7>]`. There are also release-blocking gaps in cancellation async handling, role enforcement, server-side pregnancy constraints, clarification after patient identification, and a destructive migration.

Assessment:

- **Covered:** API endpoint wrappers; core payload shape; TEMP_DISABILITY day markers; getComposition; verbatim print form; basic search; create/sign polling framework; core status/author guards; ERLN integration display/retry entry point; category and preperson UI rules.
- **Partial:** role/legal-entity restrictions, authentication method handling, newborn duplicate handling, pregnancy periods, continuation/refinement, cancellation, ERLN retry, async recovery.
- **Missing/broken:** signed createComposition invocation, reachable initial KEP create action, persistent polling for cancel/retry, complete clarification workflow after identification, comprehensive NEWBORN and end-to-end lifecycle tests.

## Highest-priority PR follow-up

These should be fixed in PR #645 rather than split into a new module PR:

1. **Repair the create/sign sequence.** Implement a real initial KEP action that validates the form, maps the composition, signs that payload, and sends `['data' => $signedContent]`; remove or correct the nonexistent `submitComposition` binding. Add a full Livewire flow test.
2. **Implement persistent async handling for cancel and ERLN retry.** Store returned job IDs/status, poll the job endpoint, update local state only on DONE, and surface FAILED details.
3. **Enforce exact role/entity combinations.** МВН: OUTPATIENT + SPECIALIST. МВТН: PRIMARY_CARE + DOCTOR or OUTPATIENT + SPECIALIST, according to TV. Test disallowed cross-combinations.
4. **Replace the destructive migration.** Use a forward, data-preserving schema/data migration. An unconditional table drop is not safe for deployment.
5. **Make pregnancy periods server-authoritative.** Fail closed if configuration cannot load, validate the submitted end date against the exact configured set, and distinguish NEW / APPENDED / REPLACEMENT correctly.
6. **Complete identification clarification UX and guards.** After merge/identification, expose the last relevant preperson SICKNESS МВТН and create a guarded `replaces` composition for the identified person. Validate chain ownership/type/status from fresh eHealth data.
7. **Harden bypassable UI rules.** Enforce preperson category and warning acknowledgment in the server action; validate selected auth method; recheck integration immediately before cancellation; turn the МВН duplicate warning into an eHealth-backed guard if TV requires uniqueness.
8. **Remove sensitive payload logging** from `reviewDetails()`.

The gaps are substantial but remain within the existing composition module. They do **not** justify a separate module PR; they are follow-up work required to make PR #645 match its “full implementation” claim.

- Endpoint/path tests for create, async job, get, search, sign, cancel, print, integration, and ERLN retry.
- Mapper tests for FHIR coding/reference shape, extensions, relations, preperson references, and fixed period markers.

Material omissions:

- No test proves initial mapper payload is KEP-signed and wrapped under `data`.
- No create → poll → getComposition → sign → poll → FINAL end-to-end test.
- No Livewire tests for search, details, print rendering, cancel, cancellation polling, integration sync, or ERLN retry polling.
- No tests for pregnancy configuration and server validation.
- No tests for preperson SICKNESS warning enforcement.
- No tests for post-identification clarification.
- No role/entity cross-product tests (for example OUTPATIENT DOCTOR attempting МВН).
- No test for duplicate МВН blocking.
- No migration preservation test.

Tests were **not executed during this audit**. Workspace rules require explicit user approval before running Laravel tests because this suite uses `RefreshDatabase` and custom `migrate:fresh`; static inspection was sufficient to identify the blockers above.

## Conclusion

PR #645 is a strong scaffold and covers most named TV 3.8 concepts, but it is **not acceptance-ready**. The top blockers are the broken unsigned create path/nonexistent action, missing async completion for cancellation and ERLN retry, incomplete role enforcement, unsafe destructive migration, and incomplete pregnancy/identified-preperson clarification safeguards.
